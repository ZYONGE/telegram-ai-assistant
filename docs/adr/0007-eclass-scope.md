# ADR 0007 — 6단계 결정: eClass 수집 구조와 수집 범위 자동 결정

- 날짜: 2026-09-20
- 상태: 채택
- 관련: CLAUDE.md 6절(eClass 규칙), 4-1절(통합 설계 원칙), 8절(eclass-cli 참고), `docs/refs/eclass-paths.md`

## 배경

학교 eClass에는 공개 API가 없고 볼 수 있는 화면이 100개가 넘는다. 그중 무엇을 가져와 무엇을 알릴지를
정해야 하는데, 두 가지가 문제였다.

1. **화면이 너무 많다.** 실제로 훑어 보니 102개 화면 중 목록형이 27개였고, 거기에는 FAQ 74줄·설문 20줄·
   소모임 15줄처럼 알릴 값어치가 없는 것이 섞여 있다. 전부 알리면 하루 알림 상한 5건을 오전에 다 쓴다.
2. **사람이 화면 목록을 적어 두는 방식은 오래가지 못한다.** 학기마다 메뉴가 바뀌고, 학교가 다르면 경로도
   다르다. 설정 파일에 화면 이름을 하나씩 적는 방식은 처음 한 번은 되지만 그다음이 없다.

## 결정

### 1. 화면 하나에 소스 하나

`app/collectors/eclass/sources/`에 소스를 둔다. 소스는 다섯 가지를 갖춘다.

| 항목 | 뜻 |
|---|---|
| `key` | 소스 이름. 저장된 항목의 출처이자 주기 기록의 열쇠라 한번 정하면 바뀌지 않는다 |
| `label` | 사용자에게 보일 이름. 알림 문구에 그대로 쓰인다 |
| `interval` | 이 화면을 얼마 만에 한 번 볼지 |
| `fetch` | 화면을 열어 `EclassItem` 목록으로 바꾼다 |
| `event_for` | 저장소가 알려 준 변화를 알릴 이벤트로 바꾼다. 알릴 것이 없으면 None |

수집기 본체(`collector.py`)는 켜진 소스를 돌리고 결과를 모으기만 한다. 새 화면을 붙일 때 본체를 고치지 않는다.
**한 소스가 실패해도 나머지는 계속 돈다.** 실패한 소스만 이름을 붙여 `collector_failed`로 올리고,
돌린 소스가 전부 실패했을 때만 수집기 자체의 연속 실패로 센다.

소스별 마지막 수행 시각은 `eclass_source_state` 표가 기억한다. 주기가 된 소스만 돌린다.

### 2. 수집 범위는 탐색 결과에서 자동으로 정한다

```
scripts/eclass_explore.py  →  private/eclass_catalog.json  →  범위 결정  →  private/eclass_scope.json
      (화면을 훑는다)              (어디를 어떻게 여는가)        (규칙→모델)      (무엇을 어떻게 다루는가)
```

처리 수준은 넷이다: `notify`(알린다) · `brief`(브리핑에만) · `store`(저장만) · `off`(건드리지 않음).

정하는 순서는 **경로 → 메뉴 이름 → 목록인지·마감이 있는지**이고, 규칙이 못 정한 화면만 가벼운 모델에게 묻는다.
실제 카탈로그에서 모델이 판단한 것은 102개 중 1개였다. **모델이 꺼져 있어도 규칙만으로 끝까지 돈다.**

낱말 목록은 `config.toml`에 둔다(개인정보가 아니다). 사용자가 대화로 바꾼 것(`eclass_scope_set`, 확인 버튼)은
다시 정할 때 덮어쓰지 않고, 그날 과목방에 못 들어가도 남는다.

### 3. 알림이 넘치지 않게 하는 장치 넷

- **꺼 두는 것을 먼저 가린다.** 경로 규칙은 `off` → `notify` → `store` 순으로 본다. 켜는 쪽이 되돌리기 쉽다.
- **마감이 있는 것은 할 일 화면 한 곳에서만 알린다.** 과제·시험·온라인강의는 과목방 게시판에도 있지만
  그쪽은 저장만 한다. 같은 것을 두 번 알리지 않는다.
- **처음 보는 화면의 지난 글은 조용히 담는다.** 게시판을 처음 열면 지난해 글까지 전부 "새 글"이다.
  7일 안에 올라온 글만 알린다. 올린 시각이 없는 항목(할 일)은 그대로 알려 할 일 등록이 빠지지 않게 한다.
- **한 번에 돌리는 소스 수를 제한한다.** 8개, 그중 과목방 화면은 2개까지. 과목방 화면은 과목마다 문을
  열어야 해서 한 소스가 수십 번 요청한다. 밀린 소스는 **오래 기다린 순**으로 다음 차례에 먼저 온다.

### 4. 급한 소식은 코드 규칙으로 가린다

마감이 코앞인 것은 날짜로 알지만, 휴강·시험 일정 변경은 글을 읽어야 안다. 제목과 본문 앞 300자에서
정해 둔 낱말을 찾는다(`config.toml`의 `urgent_words`). **애매한 낱말은 넣지 않는다.** 놓치는 것보다
잘못 울리는 쪽이 성가시다. 실제 표본에서 과목 공지 7건 중 2건, 학교 공지 22건 중 1건만 걸렸다.

### 5. 본문까지 저장하고 말로 찾는다

제목만으로는 "지난주 공지 뭐였지?"에 답할 수 없다. 알릴 화면의 **새 글만** 한 번에 5건까지 본문을 읽어 온다
(글마다 화면을 한 번 더 열어야 해서 값이 비싸다). 찾기는 `eclass_search` 도구가 한다. 도구 결과 첫 줄에
"학교 사이트에서 가져온 내용"이라고 밝혀, 모델이 그 안의 문장을 지시로 받아들이지 않게 한다 (절대 규칙 8).

## 레퍼런스(eclass-cli)와 다르게 한 점

**코드는 옮기지 않았다.** 경로와 화면 구조는 `scripts/eclass_explore.py`로 실제 사이트를 훑어 직접 확인했고
(`docs/refs/eclass-paths.md`), 파서·세션·소스는 전부 새로 썼다. 옮긴 코드가 없으므로
`THIRD_PARTY_NOTICES.md`는 만들지 않는다 (CLAUDE.md 8절).

| 항목 | eclass-cli | 이 저장소 |
|---|---|---|
| 로그인 | 학교 포털 SSO를 거쳐 eClass로 진입, 단계마다 도달 URL로 성공 판정 | eClass 자체 로그인 폼을 직접 쓴다. **실패해도 메인 주소로 보내 주므로** URL로는 판정할 수 없어 화면의 로그아웃 표시로 가린다. 로그인 단추가 `<div onclick>`이라 Enter로는 넘어가지 않아 눌러야 한다 |
| 파싱 실패 | zod 스키마 검증에서 실패시킨다 | 예외로 만들지 않는다. 줄마다 건너뛰고 **몇 줄을 못 읽었는지 센다.** 전부 못 읽었을 때만 구조 변경으로 보고한다. 한 과목이 막혀도 나머지 과목은 계속 읽는다 |
| 다룰 화면 | 코드에 박혀 있다 (과목·과제·강의자료 세 서비스) | 탐색 결과에서 자동으로 만들어진다. 설정 파일에 화면 이름을 적지 않는다 |
| 파서 | 화면마다 파서를 따로 둔다 | 게시판은 **한 파서**로 읽는다. 글번호 이름이 화면마다 달라(`ARTL_NUM`·`RT_SEQ`·확인란) 차례로 보고, 칸이 둘 이상인 줄만 센다. 게시판이 아닌 화면(강의계획서)만 전용 소스를 둔다 |
| 쓰임새 | 사용자가 명령할 때 조회하는 CLI | 스스로 주기마다 모아 **알림 게이트**를 거쳐 먼저 알린다. 모은 것은 할 일·일정 저장소로 모인다 (4-1절) |
| 마감 수집 | 할 일 목록 한 번으로 전 과목 마감을 모은다 | 같은 방식을 쓰되, 과목방 과제 게시판은 저장만 해서 **같은 마감을 두 번 알리지 않는다** |
| 본문 | 다루지 않는다 | 알릴 글만 본문까지 저장하고 `eclass_search`로 찾는다 |
| 급한 소식 | 없다 | 휴강·시험 변경을 낱말로 가려 즉시 알린다 |

## 결과

- 화면 102개 → 가져올 것 28개(알림 13·브리핑 1·저장만 14), 끄는 것 49개.
- 실제로 모은 것: 전체 공지 22건 · 과목 공지 15건(본문 5건) · 쪽지 10건 · 강의계획서 15건 · 할 일 12건.
- 첫 수집 때 알림 32건이 나올 뻔한 것을 3건으로 줄였다.

## 남은 것

- **학사일정은 eClass 화면이 비어 있다.** 세 가지 요청 방식 모두 확인했다. 학교 포털을 따로 봐야 하므로
  7단계(교환학생·학사)와 함께 다룬다.
- 온라인강의(`online_list.acl`)는 빈 응답이 와서 요청 방식 확인이 더 필요하다. 마감은 할 일 화면이
  이미 알리므로 급하지 않다.
- 게시판 검색은 낱말 포함 방식이다. 느려지면 SQLite FTS5로 바꾼다 (보관함 검색과 같은 문제).
