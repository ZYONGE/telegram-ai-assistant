# 0002. 예약 작업은 우리 표가 원본, APScheduler는 시각 계산만

- 상태: 채택 (2026-09-18, 3단계)
- 참고: NanoClaw 예약 작업 (`docs/refs/nanoclaw.md`)
- 코드: `app/scheduler/tasks.py`, `app/storage/tasks.py`, `app/tools/tasks.py`

## 배경

대화로 리마인더와 예약 작업을 등록·조회·일시정지·취소해야 하고, 재시작 후에도 예약이 유지되어야 한다. 확정 스택은 APScheduler + SQLite다.

## 결정

- `scheduled_tasks` 표가 작업의 원본이다 (내용, 1회 시각 또는 cron, 상태, 연속 실패 수). 실행 기록은 `task_runs`에 남긴다.
- APScheduler는 메모리 작업 저장소만 쓴다. 시작할 때 활성 작업을 모두 다시 등록한다. job id는 작업 id와 같다.
- 발송은 알림 게이트를 거치며, 사용자가 요청한 작업이라 조용한 시간·일일 상한의 예외가 된다.

## NanoClaw에서 가져온 것

- 1회성(`run_at`)과 반복(`cron`)을 같은 형식으로 표현하고, 둘 중 하나만 허용한다.
- 상태 구분: 활성 / 일시정지 / 완료 / 취소. 취소는 기록을 남긴다.
- cron은 사용자 시간대(Asia/Seoul)로 해석하고 시각은 UTC로 저장한다.
- 빈도 제한: 모델을 부르는 작업은 24시간에 4회 이하.
- 연속 실패가 쌓이면 자동으로 일시정지하고 알린다.
- 짧고 읽기 쉬운 작업 ID (`t-xxxxxx`).
- 입력 검증과 저장을 나눠, 잘못된 입력은 도구 결과로 모델에게 돌려준다.

## 원본과 다르게 한 점

| NanoClaw | 우리 | 이유 |
|---|---|---|
| 60초 스윕 + 회차마다 행을 복제 | APScheduler가 시각 계산, 표는 작업당 한 행 | 확정 스택. 두 저장소(APScheduler 영속 저장소와 우리 표)의 불일치를 피하려고 APScheduler 영속 저장소는 쓰지 않는다 |
| Bash 스크립트 게이트 (모델이 작성) | 없음. 점검은 코드에 정의된 수집기만 한다 | 셸 실행 금지 (절대 규칙 5) |
| 모든 작업을 에이전트 세션으로 실행 | 리마인더는 모델 없이 저장된 문장을 보낸다. `agent` 작업만 모델을 부른다 | 비용, "알릴 내용이 있을 때만 모델 호출" |
| 반복 실패 시 2~60분 지연 | 반복 작업은 지연 없이 8회 연속 실패 시 일시정지, 1회성은 5분 간격 3회 재시도 | cron 주기를 그대로 두는 편이 단순하다 |
| 리마인더 빈도 제한 동일 | 리마인더는 24시간 48회, 에이전트 작업은 4회 | 리마인더는 모델 비용이 없다 |
| 모델이 delete로 기록까지 삭제 가능 | 모델 도구는 cancel까지만 | 되돌릴 수 없는 조작 최소화 |
| 결과 전달처를 프롬프트로 지정 | 사용자 1명, 알림 게이트로 고정 | CLAUDE.md 4-1 |
