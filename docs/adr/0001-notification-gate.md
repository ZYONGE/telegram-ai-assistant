# 0001. 알림 게이트는 코드 규칙으로 결정한다

- 상태: 채택 (2026-09-17, 2단계)
- 참고: nanobot 하트비트의 알림 평가 (`docs/refs/nanobot.md`)
- 코드: `app/scheduler/gate.py`, `app/scheduler/dispatcher.py`

## 배경

비서는 수집기·예약 작업·브리핑에서 먼저 말을 건다. 조용한 시간(23:00~06:30)과 하루 알림 상한은 반드시 지켜야 하고, 같은 소식을 두 번 보내면 안 된다.

## 결정

- 모든 선제 이벤트는 `Dispatcher.publish()` 한 곳을 거친다. 수집기·스케줄러는 채널을 직접 부르지 않는다.
- `RuleBasedGate`가 순서대로 판단한다: 중복(ref_id) → 조용한 시간 → 사용자 요청·브리핑 → 급한 소식(일일 상한) → 브리핑 묶음.
- 결정은 `notifications` 표에 남기고, 보류가 풀렸거나 발송에 실패한 알림은 1분마다 다시 판단한다.

## nanobot에서 가져온 것

- 선제 발송은 관문 하나만 통과한다 (하트비트 실행 중 메시지 도구의 직접 발송을 막는 구조).
- 판단이 불확실하면 알리지 않는 쪽(fail-closed)을 택한다. 우리 구조에서는 이미 처리한 이벤트를 다시 보내지 않고, 발송 실패 시 기록을 남겨 재시도한다.
- 알릴 거리가 없으면 모델을 부르지 않는다.

## 원본과 다르게 한 점

| nanobot | 우리 | 이유 |
|---|---|---|
| 보낼지 말지를 LLM(`evaluate_notification`)이 판단 | 코드 규칙으로 결정. 모델은 문장만 다듬는다 | 조용한 시간·상한은 코드에서 강제한다는 확정 사항. 같은 입력이면 같은 결정이 나와야 테스트할 수 있다 |
| 결과를 보내거나 버리는 두 가지 | `send_now` / `batch` / `hold` / `drop` 네 가지 | 조용한 시간 보류와 브리핑 이월이 필요하다 |
| 중복 방지 개념 없음 | ref_id로 중복 제거, 회차별 고정 ref_id | 수집기가 같은 글을 반복해서 가져온다 |
